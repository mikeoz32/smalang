# ADR 0004: AST lowering масивів і низькорівневі операції пам'яті

## Статус

Прийнято. `alloc_stack` і скалярний `offset` реалізовані за [ADR 0003](0003-unsafe-memory-operations.md); `cast`, `stack_storage`, `size_of`, `align_of`, `address_of`, `heap_storage` і `heap_free` з Memory API нижче реалізовані. `copy_memory` та AST desugaring масивів ще не реалізовані.

## Контекст

Масиви вже реалізовані через спеціалізовані array types та операції в typed IR і backend. Raw-вказівники наразі підтримують одноелементні heap-виділення скалярів через `alloc`, `load`, `store` і `free`. `address_of` дає source-коду доступ до фактичного сховища скалярних локальних змінних і параметрів; масиви й інші складені bindings поки не підтримуються.

[ADR 0002](0002-ast-desugaring.md) визначає desugaring у межах одного AST. Це рішення конкретизує його для масивів: frontend перевіряє масивні правила й розгортає масиви в низькорівневі вузли пам'яті до AST-to-IR lowering. Ці самі примітиви мають бути доступні користувачеві через явний `unsafe` API.

## Рішення

### Конвеєр і межі відповідальності

```text
Parser → AST із масивними конструкціями
       → source semantic checks
       → AST-to-AST desugaring у тій самій моделі AST
       → перевірка типів та інваріантів згенерованих вузлів
       → AST-to-IR lowering низькорівневих операцій
       → typed IR → backend
```

- Масив має семантичний тип `array[T, N]` до проходів, які використовують `T` і `N` для перевірок та зниження. IR і backend мають отримувати загальні операції сховища, адресації, доступу й копіювання пам'яті замість спеціалізованих `array.get`/`array.set`.
- Окремий Core AST та обов'язковий додатковий IR-to-IR pass для цього не вводяться. Семантичний аналіз сам AST не переписує; desugaring є наступним окремим проходом.
- Layout-дані про розмір, вирівнювання й крок елемента можуть залишатися доступними IR. Усунення array-операцій не вимагає втрачати відомі під час компіляції властивості пам'яті.
- IR verifier продовжує перевіряти типи, SSA, CFG та контракти операцій. Згенероване походження вузла не дозволяє пропускати перевірку коректності IR.
- Кожен pass явно визначає вхідні та вихідні інваріанти, оновлює семантичні факти для нових `NodeId` і зберігає source locations. Нові вузли не повинні мати непомітно застарілих типів або посилань на старі semantic facts.
- Ефекти читання, запису, виділення, звільнення та винятків мають зберігати порядок. Відомі layout, alignment і властивості aliasing можна передавати далі лише тоді, коли вони доведені.

### Семантика масивів

Зберігається контракт [ADR про фіксовані масиви](../docs/adr/0001-fixed-size-arrays.md): `N` відоме під час компіляції, елементи розташовані inline підряд, вкладені й порожні масиви дозволені, ініціалізатор обов'язковий, неявного нульового заповнення немає. Користувацькі літерали мають рівно `N` compile-time constant елементів. Індекс має тип `uint`, запис потребує `mut`, присвоєння, параметри й результати функцій копіюють елементи.

Адреса, яку lowering використовує для масиву, є способом доступу до його сховища. Копіювання цієї адреси саме по собі не реалізує копіювання масиву за значенням. Для незалежного одержувача lowering забезпечує окреме сховище й копіювання; фізичну копію можна усунути лише зі збереженням спостережуваної поведінки.

Тип масиву не задає обов'язкового heap-виділення. Поточний зріз використовує локальне сховище в кадрі функції. Глобальні масиви й масиви всередині heap-об'єктів потребуватимуть відповідних способів розміщення. `N` не потрібно дублювати runtime-полем довжини у фіксованому масиві.

### Універсальний Memory API

Усі операції нижче є частиною користувацького unsafe API й доступні лише всередині `unsafe:`. AST-to-AST desugaring викликає ті самі операції, що й користувацький код; окремі compiler-only аналоги не вводяться. `bytes` задає повний розмір області в байтах як `uint`, а не кількість елементів або множник до розміру типу. Переповнення при розрахунку розміру чи вирівнювання не допускається: compile-time переповнення є помилкою компіляції, а runtime-переповнення породжує runtime-помилку некоректного аргументу до використання результату.

`ptr[T]` є non-nullable raw-вказівником; null pointers і nullable pointer types не підтримуються. `cast[U]` змінює лише статичний тип вказівника, зберігаючи адресу, і не створює null. У першій реалізації `T` та `U` мають бути скалярними типами. Cast не перевіряє валідність пам'яті, вирівнювання чи lifetime. Pointer arithmetic в `unsafe`, що породжує нульову адресу, порушує контракт; обов'язкових runtime-перевірок для цього немає. Складені значення адресуються через `ptr[uint8]`, байтові зміщення та вказівники на конкретні скалярні поля; підтримка складених pointee в IR не потрібна.

| Операція | Контракт | Статус |
| --- | --- | --- |
| `cast[U](address: ptr[T]) -> ptr[U]` | Повертає ту саму адресу зі статичним типом `ptr[U]`; не перевіряє валідність, alignment або lifetime. | Нова універсальна операція перетворення вказівника. |
| `stack_storage(bytes: uint, alignment: uint) -> ptr[uint8]` | Резервує неініціалізовану область заданого розміру й вирівнювання в кадрі поточної функції. `bytes` і `alignment` мають бути compile-time constants; `bytes` має бути ненульовим. Адреса чинна лише до завершення кадру й не звільняється через `heap_free` або `free`. | Нове універсальне стекове сховище. |
| `heap_storage(bytes: uint, alignment: uint) -> ptr[uint8]` | Виділяє неініціалізовану heap-область. `bytes` може бути runtime-значенням, а `alignment` має бути compile-time constant. Розмір і вирівнювання мають бути коректними, ненульовими; вирівнювання є степенем двійки. Нульовий compile-time розмір і compile-time переповнення padding — помилки компіляції. Нульовий runtime-розмір або runtime-переповнення padding породжує `InvalidArgument`; невдала алокація породжує `OutOfMemory`. | Реалізовано для Linux x86-64 через `mmap`; початкову адресу відображення зберігає приватний заголовок перед вирівняною адресою. Не змінює контракт односелярного `alloc(value)`. |
| `heap_free(address: ptr[uint8], bytes: uint, alignment: uint) -> unit` | Звільняє всю heap-алокацію, створену відповідним `heap_storage`; `alignment` compile-time, адреса, розмір і вирівнювання мають точно відповідати алокації. Невідповідні аргументи, повторне звільнення або звільнення чужої адреси є undefined behavior в `unsafe`. | Реалізовано для Linux x86-64 через `munmap`; не замінює `free(address)` для `alloc(value)`. |
| `copy_memory(dst: ptr[uint8], src: ptr[uint8], bytes: uint) -> unit` | Копіює байти із семантикою `memmove`: підтримує перекриття та самокопіювання. Для нульового розміру не читає й не записує пам'ять. | Нове універсальне копіювання представлення. |
| `size_of(T)`, `align_of(T)` | Повертають target-розмір і вирівнювання типу з визначеним layout. Розміри вкладених типів обчислюються з перевіркою переповнення. | Реалізовані як compile-time `uint` для скалярних типів і `ptr[T]` зі скалярним `T`; масивні запити відкладені. |
| `address_of(place)` | Повертає адресу фактичного сховища `place`, а не копії значення. Для address-taken locals компілятор узгоджує читання й запис через змінну та через вказівник. Адреса чинна протягом lifetime сховища; `address_of` не подовжує lifetime. Адреси складених місць представляються через `ptr[uint8]`. | Реалізований перший зріз для скалярних локальних bindings і параметрів; масиви, indexed places, globals та fields відкладені. |
| `offset(address, index)` | Обчислює адресу елемента з кроком target-розміру pointee; не читає/пише пам'ять і не перевіряє межі, alignment чи lifetime. | Зберігається за ADR 0003; поточний source-зріз приймає `uint` та скалярний `T`. |
| `load(address)` / `store(address, value)` | Читають або записують типізоване скалярне значення відповідно до target layout; `load` вимагає ініціалізованої пам'яті. Складені значення копіюються через `copy_memory`. | Зберігаються як чинні скалярні операції. Byte-buffer API використовує їх через явний `cast[U]`. |
| `alloc(value)` / `alloc_stack(value)` / `free(address)` | Наявні ініціалізовані виділення одного скаляра та їхній lifecycle за ADR 0003. | Зберігаються без змін. `alloc_stack(value)` не гарантує суміжності з іншими місцями виклику. |

Для storage-операцій `alignment` має бути compile-time constant, ненульовим степенем двійки; некоректне значення відхиляється під час компіляції. `stack_storage` вимагає compile-time constants для обох аргументів; `heap_storage` дозволяє runtime `bytes`, але не runtime `alignment`. `stack_storage(0, alignment)` і compile-time виклик `heap_storage(0, alignment)` є помилками компіляції; нульовий runtime-розмір `heap_storage` є runtime-помилкою некоректного аргументу. Розмір і padding обчислюються з перевіркою переповнення. Нижче рівня API не передаються ані count, ані множник `size_of(T)`: caller надає повний розмір у байтах. Для масиву compiler lowering обчислює total byte size із перевіркою переповнення та передає результат у storage API.

`stack_storage` і `heap_storage` не ініціалізують пам'ять. Читання до запису заборонене. Нульові алокації заборонені: нульовий розмір, відомий під час компіляції, є помилкою компіляції; нульовий runtime-розмір `heap_storage` породжує runtime-помилку некоректного аргументу, не `OutOfMemory`. `array[T, 0]` залишається дозволеним: якщо адреса не потрібна, сховище не виділяється; якщо потрібна — резервується мінімальна ненульова область із вирівнюванням типу, без права доступу до елементів. Lowering масиву записує всі елементи літерала до першого читання. `copy_memory` копіює лише representation bytes: не клонує ресурси, не передає ownership і не викликає initializer чи destructor. Автоматична копія owning-елементів потребує окремого move/clone/cleanup lowering за ADR 0001.

`heap_storage` і `heap_free` є парою для довільних буферів, а їхні адреса, розмір та вирівнювання мають відповідати одній алокації. `alloc(value)`/`free(address)` залишаються парою для чинного односелярного API. Адреси зі стеку, статичного сховища чи середини іншої алокації не передаються до `heap_free`.

`heap_free` і `copy_memory` мають результат `unit` в IR. Оскільки source-мова поки не має загального `unit`-типу та довільних expression statements, їхні source-виклики є окремими операціями й не додають синтаксису `None`.

`array`, майбутні `struct` і `class` використовують цей самий універсальний набір операцій. Спеціалізованих memory primitives для цих типів не додається.

`check_index(index, length)` лишається правилом array lowering: source-індекс відомий під час компіляції — компілятор відхиляє до desugaring; runtime-порушення породжує `IndexOutOfBounds` із source location. Окремий compiler-only Memory API для перевірки меж не додається. `check_range(start, end, length)` залишається майбутнім правилом slicing, не частиною цього unsafe API.

### Приклади розгортання

Псевдокод нижче показує послідовність дій; він не запроваджує source-синтаксис, нові імена builtin-функцій або правила виведення типів.

```text
items: array[T, N] = literal
    → якщо N > 0: storage = stack_storage(size_of(array[T, N]), align_of(array[T, N]))
    → якщо N = 0 і адреса потрібна: storage = stack_storage(1, align_of(array[T, 0]))
    → якщо N = 0 і адреса не потрібна: сховище не виділяється
    → ініціалізація всіх елементів literal у storage

items[index]
    → обчислити основу та index рівно один раз у source-порядку
    → check_index(index, N)
    → byte_offset = index * size_of(T)
    → element_address = offset(storage, byte_offset)
    → value = load(cast[T](element_address))  // для скалярного T

items[index] = value
    → перевірити mut і типи до розгортання
    → rhs = обчислити value рівно один раз
    → обчислити основу й індекси зліва направо, кожен рівно один раз
    → виконати всі check_index до першого запису
    → byte_offset = index * size_of(T)
    → element_address = offset(storage, byte_offset)
    → store(cast[T](element_address), rhs)  // для скалярного T

other = items
    → скопіювати значення в окреме сховище other
```

Для складеного `T` byte offset обчислюється так само. Значення складеного елемента копіюється між його адресою та окремим сховищем через `copy_memory`; scalar `load`/`store` для цього не використовуються. Вкладена індексація перевіряє кожен рівень і бере `size_of` відповідного вкладеного типу як крок. Для indexed assignment RHS обчислюється першим, далі основа й індекси зліва направо; кожен операнд обчислюється один раз, а всі перевірки меж завершуються до першого запису в цільове сховище. Порядок ефектів і винятків зберігається після AST-to-AST desugaring. Нульова довжина та вкладені типи нульового розміру обробляються явно: порожнє копіювання не читає пам'ять, індексування порожнього масиву завжди неуспішне. Непредставимі розміри й зміщення відхиляються до генерації некоректного доступу. Арифметика layout не повинна непомітно використовувати циклічне переповнення source-цілих.

Для параметрів і результатів масивів зберігається копіювання за значенням. ABI може використовувати адреси копій і приховане сховище результату caller-а. Повернення значення масиву не означає повернення адреси локального кадру callee.

### Unsafe, lifetime та винятки

- Source-виклики низькорівневих операцій дозволені лише у відповідному unsafe-контексті. Низькорівневі вузли, породжені desugaring, використовують ті самі контракти операцій; lowering відповідає за їхню коректність і не надає unsafe-дозволів навколишньому source-коду.
- `ptr[T]` залишається raw-адресою. Отримання стекової адреси не продовжує час життя її сховища. Source unsafe-код відповідає за валідність доступу за ADR 0003; compiler-generated адреси не можуть переживати сховище або звільнятися як heap-виділення.
- Стекове сховище недоступне після завершення відповідного кадру, включно з виходом через виняток. Самі адреси не є heap-власниками й не отримують автоматичний `free`.
- Майбутні owning heap-об'єкти підпорядковуються [ADR 0001 про ownership](0001-memory-ownership.md). Це рішення не додає GC, reference counting або borrowing і не робить raw-вказівники власниками.
- Runtime-перевірки меж і майбутні алокації зберігають normal/exceptional control flow. Source locations походять від вихідної операції масиву; stack trace не повинен показувати лише синтетичні вузли.

### IR і SIMD

AST-to-IR lowering відображає залишкові низькорівневі вузли на типізовані операції сховища, адресації й пам'яті. Їхні читання, записи та виняткові ефекти зберігаються явно. Дамп нових IR-операцій використовує наявну S-expression notation.

`load`, `store`, `copy_memory`, allocation і free мають явні memory effects в IR. `copy_memory` позначає читання джерела та запис призначення. Порядок memory operations зберігається, якщо відсутність небезпечного aliasing не доведена; SSA-значень адрес недостатньо, щоб усунути чи переставити доступи. Окремий Memory SSA для першої реалізації не потрібен.

Неперервний layout масиву зберігається після desugaring. Відомі розміри, alignment та доведені властивості aliasing мають залишатися доступними наступним проходам, щоб це зниження не закривало шлях до SIMD. SIMD-операції та типи lane-значень потребують окремого рішення; введення SIMD не вимагає змінювати семантику копіювання масивів.

## Наслідки та перехід

- Поведінка source-масивів зберігається; відповідальність за їх розгортання переноситься перед AST-to-IR lowering. Чинна реалізація в IR/backend залишається реалізованим станом до завершення міграції.
- Примітиви локального сховища, адресації, load/store й копіювання стануть спільною основою для масивів та майбутніх складених типів.
- Перед заміною чинного array lowering потрібен окремо схвалений план. Перевірки мають охопити енд-ту-енд копіювання при присвоєнні, параметрах і return; вкладені й порожні масиви; mutability; runtime-межі зі source locations; заданий порядок і одноразовість обчислення операндів; непротікання локальних адрес у результат.
- Контракти залишкового AST, memory effects, IR verifier і S-expression дампів перевіряються окремо як стабільні контракти проходів.

## Відкриті деталі перед реалізацією

Узгоджені контракти API, pointer types, indexed assignment і memory effects наведено вище. Відкритою лишається конкретна форма їхнього представлення в IR та правила перевірки цих ефектів verifier-ом; це деталь implementation plan, а не невирішена семантика.
