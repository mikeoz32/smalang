# ADR 0004: AST lowering масивів і низькорівневі операції пам'яті

## Статус

Прийнято як архітектурний напрямок; ще не реалізовано. Каталог нижче описує потрібні можливості. Назви нових операцій є умовними, остаточний source-синтаксис і невирішені деталі контрактів потребують окремого плану реалізації.

## Контекст

Масиви вже реалізовані через спеціалізовані array types та операції в typed IR і backend. Raw-вказівники наразі підтримують одноелементні heap-виділення скалярів через `alloc`, `load`, `store` і `free`. Операції отримання source-вказівника на локальне сховище немає; backend сам обчислює адреси стекових масивів від бази кадру.

[ADR 0002](0002-ast-desugaring.md) визначає desugaring у межах одного AST. Це рішення конкретизує його для масивів: frontend перевіряє масивні правила й розгортає масиви в низькорівневі вузли пам'яті до AST-to-IR lowering. Ці самі примітиви мають бути доступні користувачеві через явний `unsafe` API.

## Рішення

### Конвеєр і межі відповідальності

```text
Parser → AST із масивними конструкціями
       → source semantic checks
       → AST-to-AST desugaring у тій самій моделі AST
       → перевірка типів та інваріантів згенерованих вузлів
       → AST-to-IR lowering низькорівневих операцій
       → typed IR → backend
```

- Масив має семантичний тип `array[T, N]` до проходів, які використовують `T` і `N` для перевірок та зниження. IR і backend мають отримувати загальні операції сховища, адресації, доступу й копіювання пам'яті замість спеціалізованих `array.get`/`array.set`.
- Окремий Core AST та обов'язковий додатковий IR-to-IR pass для цього не вводяться. Семантичний аналіз сам AST не переписує; desugaring є наступним окремим проходом.
- Layout-дані про розмір, вирівнювання й крок елемента можуть залишатися доступними IR. Усунення array-операцій не вимагає втрачати відомі під час компіляції властивості пам'яті.
- IR verifier продовжує перевіряти типи, SSA, CFG та контракти операцій. Згенероване походження вузла не дозволяє пропускати перевірку коректності IR.
- Кожен pass явно визначає вхідні та вихідні інваріанти, оновлює семантичні факти для нових `NodeId` і зберігає source locations. Нові вузли не повинні мати непомітно застарілих типів або посилань на старі semantic facts.
- Ефекти читання, запису, виділення, звільнення та винятків мають зберігати порядок. Відомі layout, alignment і властивості aliasing можна передавати далі лише тоді, коли вони доведені.

### Семантика масивів

Зберігається контракт [ADR про фіксовані масиви](../docs/adr/0001-fixed-size-arrays.md): `N` відоме під час компіляції, елементи розташовані inline підряд, вкладені й порожні масиви дозволені, ініціалізатор обов'язковий, неявного нульового заповнення немає. Користувацькі літерали мають рівно `N` compile-time constant елементів. Індекс має тип `uint`, запис потребує `mut`, присвоєння, параметри й результати функцій копіюють елементи.

Адреса, яку lowering використовує для масиву, є способом доступу до його сховища. Копіювання цієї адреси саме по собі не реалізує копіювання масиву за значенням. Для незалежного одержувача lowering забезпечує окреме сховище й копіювання; фізичну копію можна усунути лише зі збереженням спостережуваної поведінки.

Тип масиву не задає обов'язкового heap-виділення. Поточний зріз використовує локальне сховище в кадрі функції. Глобальні масиви й масиви всередині heap-об'єктів потребуватимуть відповідних способів розміщення. `N` не потрібно дублювати runtime-полем довжини у фіксованому масиві.

### Каталог потрібних примітивів

Тут `T` — відомий компілятору тип із визначеним layout, `count` — кількість елементів, а `bytes` — кількість байтів. Записи є позначеннями можливостей, а не затвердженими сигнатурами builtin-функцій. Каталог не означає, що чинний `ptr[T]` уже підтримує довільний `T`.

| Можливість | Потрібний контракт | Обсяг |
| --- | --- | --- |
| `size_of(T)`, `align_of(T)` | Розмір і вирівнювання для target обчислюються під час компіляції. Крок елемента враховує layout вкладених значень. | Потрібні для зниження масивів; публічний API ще не визначений. |
| `stack_storage(T, N)` | Резервує локальне сховище з відомими під час компіляції розміром і вирівнюванням та надає адресу. Backend призначає конкретний зсув у кадрі. Дані потрібно ініціалізувати перед читанням; автоматичного заповнення немає. | Перший зріз масивного desugaring; runtime-розмір стека не додається. |
| `address_of(place)` | Отримує адресу наявного адресованого сховища без нової алокації або копіювання. Для локального значення backend за потреби матеріалізує сховище в кадрі. | Потрібна для використання наявних локальних сховищ; globals і поля додаються разом із відповідними фічами. |
| `offset(address, index)` | Обчислює адресу елемента з кроком `size_of(T)`, без читання чи запису. Сам raw-доступ не доводить межі, вирівнювання або час життя. | Перший зріз використовує чинні `uint`-індекси масивів. Від'ємні зміщення не визначаються цим ADR. |
| `load(address)` | Читає типізоване ініціалізоване значення з валідної адреси з належним вирівнюванням. Для `bool` зберігається чинний контракт канонічних `0`/`1`. | Чинний скалярний примітив; зниження складених значень використовує layout і копіювання. |
| `store(address, value)` | Записує значення відповідного типу у валідну доступну для запису область. Ширина запису відповідає target-layout. | Чинний скалярний примітив. |
| `copy_memory(destination, source, bytes)` | Переносить представлення значення між сховищами. Потрібно визначити контракт перекриття областей; lowering повинен зберігати семантику присвоєння і для `a = a` та можливого перекриття. | Потрібна можливість для копіювання масивів; окремі memcpy/memmove API ще не узгоджені. |
| `check_index(index, length)` | Вимагає `index < length`. Відомий неправильний source-індекс відхиляється до desugaring; runtime-порушення веде до чинного `IndexOutOfBounds` із source location. | Потрібна для змінного індексу. Може розгортатися в порівняння й винятковий перехід без окремої IR array-операції. |
| `alloc(value)` / `free(address)` | Чинне виділення й ініціалізація одного скаляра та звільнення відповідного heap-виділення за ADR 0003. | Уже реалізовані; `free` не застосовується до стеку, статичних адрес або внутрішньої адреси елемента. |
| Виділення й звільнення буфера `T × count` | Виділяє contiguous область із потрібним вирівнюванням. Розмір `count × size_of(T)` перевіряється перед алокацією. Звільнення має отримувати або відновлювати потрібні allocation/layout/allocator-дані; одного `ptr[T]` недостатньо, щоб завжди знати розмір виділення. | Майбутні динамічні контейнери; source API, ініціалізація та повідомлення про переповнення розміру ще не визначені. Нестача пам'яті використовує `OutOfMemory`. |
| Адреса статичного сховища | Адресує символ у статичній пам'яті; backend формує потрібні sections і relocations. Час життя відповідає глобальному сховищу, доступність запису — його кваліфікаторам. | Майбутні глобальні значення; не передумова локальних масивів. |
| `check_range(start, end, length)` | Для майбутнього слайса перевіряє `start <= end <= length`; після перевірки обчислюються початкова адреса й довжина. | Вимога до майбутнього slicing; синтаксис, ownership і lifetime слайсів цим ADR не визначаються. |

`copy_memory` копіює сире представлення даних; вона не клонує ресурси, не передає ownership і не викликає ініціалізатори або деструктори. Автоматичне копіювання масивів цим проходом обмежене нинішніми дозволеними елементами: цілими, `bool` і вкладеними масивами цих типів. Копіювання майбутніх owning-типів не можна реалізувати простим дублюванням байтів; їхній move/clone/cleanup підпорядковується ADR 0001 і потребує окремого зниження.

Для нинішніх типів даних виділення нового буфера, копіювання потрібних елементів і звільнення старого можуть виражати ріст майбутнього контейнера. Окрема операція `realloc` не є передумовою цього рішення. Casts вказівників, перетворення адрес у цілі числа, `memset`, SIMD, atomics і volatile-доступ не додаються як приховані вимоги першого зрізу масивів.

### Приклади розгортання

Псевдокод нижче показує послідовність дій; він не запроваджує source-синтаксис, нові імена builtin-функцій або правила виведення типів.

```text
items: array[T, N] = literal
    → storage = stack_storage(T, N)
    → ініціалізація всіх елементів literal у storage

items[index]
    → обчислити основу та index рівно один раз у source-порядку
    → check_index(index, N)
    → load(offset(storage_address, index))

items[index] = value
    → перевірити mut і типи до розгортання
    → обчислити операнди рівно один раз у визначеному мовою порядку
    → check_index(index, N)
    → store(offset(storage_address, index), value)

other = items
    → скопіювати значення в окреме сховище other
```

Вкладена індексація перевіряє кожен рівень і використовує крок вкладеного типу. Нульова довжина та вкладені типи нульового розміру обробляються явно: порожнє копіювання не читає пам'ять, індексування порожнього масиву завжди неуспішне. Непредставимі розміри й зміщення відхиляються до генерації некоректного доступу. Арифметика layout не повинна непомітно використовувати циклічне переповнення source-цілих.

Для параметрів і результатів масивів зберігається копіювання за значенням. ABI може використовувати адреси копій і приховане сховище результату caller-а. Повернення значення масиву не означає повернення адреси локального кадру callee.

### Unsafe, lifetime та винятки

- Source-виклики низькорівневих операцій дозволені лише у відповідному unsafe-контексті. Низькорівневі вузли, породжені desugaring, використовують ті самі контракти операцій; lowering відповідає за їхню коректність і не надає unsafe-дозволів навколишньому source-коду.
- `ptr[T]` залишається raw-адресою. Отримання стекової адреси не продовжує час життя її сховища. Source unsafe-код відповідає за валідність доступу за ADR 0003; compiler-generated адреси не можуть переживати сховище або звільнятися як heap-виділення.
- Стекове сховище недоступне після завершення відповідного кадру, включно з виходом через виняток. Самі адреси не є heap-власниками й не отримують автоматичний `free`.
- Майбутні owning heap-об'єкти підпорядковуються [ADR 0001 про ownership](0001-memory-ownership.md). Це рішення не додає GC, reference counting або borrowing і не робить raw-вказівники власниками.
- Runtime-перевірки меж і майбутні алокації зберігають normal/exceptional control flow. Source locations походять від вихідної операції масиву; stack trace не повинен показувати лише синтетичні вузли.

### IR і SIMD

AST-to-IR lowering відображає залишкові низькорівневі вузли на типізовані операції сховища, адресації й пам'яті. Їхні читання, записи та виняткові ефекти зберігаються явно. Дамп нових IR-операцій використовує наявну S-expression notation.

Неперервний layout масиву зберігається після desugaring. Відомі розміри, alignment та доведені властивості aliasing мають залишатися доступними наступним проходам, щоб це зниження не закривало шлях до SIMD. SIMD-операції та типи lane-значень потребують окремого рішення; введення SIMD не вимагає змінювати семантику копіювання масивів.

## Наслідки та перехід

- Поведінка source-масивів зберігається; відповідальність за їх розгортання переноситься перед AST-to-IR lowering. Чинна реалізація в IR/backend залишається реалізованим станом до завершення міграції.
- Примітиви локального сховища, адресації, load/store й копіювання стануть спільною основою для масивів та майбутніх складених типів.
- Перед заміною чинного array lowering потрібен окремо схвалений план. Перевірки мають охопити енд-ту-енд копіювання при присвоєнні, параметрах і return; вкладені й порожні масиви; mutability; runtime-межі зі source locations; порядок і одноразовість обчислення операндів; непротікання локальних адрес у результат.
- Контракти залишкового AST, memory effects, IR verifier і S-expression дампів перевіряються окремо як стабільні контракти проходів.

## Відкриті деталі перед реалізацією

- Остаточні імена, типові аргументи, сигнатури й резервування імен публічного unsafe API; які типи дозволені в `ptr[T]` після розширення.
- Точне співвідношення локального storage-вузла й `address_of`, та доступність обох можливостей у source API.
- Контракт перекриття для публічного копіювання; підтримка pointer arithmetic за межами чинних невід'ємних масивних індексів.
- Контракт буферного allocator/deallocator, зберігання розміру виділення та діагностика переповнення allocation-size.
- Остаточні правила source-порядку обчислення основи, індексу й RHS indexed assignment та їх збереження при винятках.
- Представлення layout і memory effects у простому IR та узгодження перевірок AST/IR verifier. Це деталі майбутнього плану, а не вже реалізовані можливості.
