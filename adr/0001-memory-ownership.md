# ADR 0001: Володіння пам'яттю, move та clone

Статус: прийнято як архітектурний напрямок; ще не реалізовано.

## Контекст

Smalang потребує безпечного керування часом життя heap-об'єктів із перевірками під час компіляції, без GC, reference counting і borrowing.

## Рішення

Наведені нижче правила є вимогами до майбутніх heap-об'єктів; `move`, `clone` та їхні перевірки ще не реалізовані. Решта синтаксису й правила для конкретних складених типів визначатимуться окремо.

- Кожен ресурс має одного власника. Спільні owning-посилання й позичання не входять до цієї моделі.
- `move` передає володіння без клонування ресурсу. Попередній власник стає недоступним; читання, повторне передавання чи знищення через нього відхиляються під час компіляції.
- Явний `move` дозволений лише в аргументах виклику: `consume(move data)`. Самостійне присвоєння `b = move a` та інші використання `move` поза аргументами заборонені.
- Виклик може передати володіння параметру, а `return` — повернути його викликувачу. Об'єкт може пережити scope створення через передавання володіння.
- `clone` є явною операцією, що створює незалежний об'єкт із власним володінням його ресурсами. Неявне клонування та приховане спільне володіння заборонені.
- Прості скаляри, зокрема `bool` і цілі числа, копіюються. Власники об'єктів не копіюються через `b = a`: для незалежного об'єкта потрібна явна операція clone. Передавання наявного власника аргументом також потребує явного `move` або `clone`; наявність реалізації `clone` не дозволяє неявних копій.
- Якщо володіння не передане далі, ресурс знищується автоматично при завершенні часу життя власника, включно з виходом через виняток. Звичайний код не звільняє owned-пам'ять вручну.
- Коректність часу життя й передавання володіння перевіряється під час компіляції. GC, reference counting і runtime-перевірки валідності посилань не використовуються для цього. Виконання алокації, деструкторів і звільнення пам'яті відбувається під час роботи програми.
- Алокатори є окремим майбутнім механізмом. Передавання володіння об'єктом не продовжує час життя пам'яті його алокатора; об'єкт не може пережити свою область пам'яті. Безпечні локальні arenas потребуватимуть статичного доведення цієї умови.

Повна незмінність даних і чистота функцій поки є предметом обговорення. Вони не замінюють правила часу життя пам'яті та не змінюють чинну семантику `const[T]` і `mut[T]`.

## Наслідки

- Передавання об'єктів потребує явного вибору між передаванням володіння та незалежним клонуванням.
- Функція, яка отримала власника, може повернути його через return для подальшого використання викликувачем.
- Компілятор має перевіряти доступ після передавання володіння та генерувати коректне знищення ресурсів на звичайних і виняткових шляхах.

## Відкриті питання

- Повний синтаксис створення об'єктів, клонування та повернення власників.
- Контракт доступу операції clone до початкового власника за відсутності borrowing; остаточний API ще не визначений.
- Правила володіння вкладеними ресурсами й часткового переміщення.
- Представлення об'єктів, інтерфейс алокаторів і статичні обмеження локальних arenas.
- Повна immutability та модель ефектів функцій.
