# ADR 0003: Unsafe-операції з пам'яттю

Статус: прийнято як архітектурний напрямок; ще не реалізовано. Наведені назви й приклади задають зміст API; точні сигнатури та синтаксис визначатимуться окремо.

## Контекст

Runtime, алокатори, контейнери та майбутній C FFI потребують доступу до пам'яті за адресами. Ці можливості доступні через явний unsafe-контекст, а не через привілей за назвою пакета stdlib.

## Рішення

- `ptr[T]` представляє raw-адресу пам'яті з очікуваним типом значення `T`. Він не є власником, не звільняє пам'ять і сам по собі не доводить її валідність, довжину чи час життя.
- Сам вказівник може зберігатися в регістрі, на стеку або полем об'єкта. Алокація за вказівником виділяє пам'ять для даних, а не обов'язково для самого значення адреси.
- Небезпечні операції дозволені лише в явно позначеному unsafe-контексті. Передбачаємо unsafe-блоки й unsafe-функції; виклик unsafe-функції потребує unsafe-контексту.
- Unsafe не вимикає звичайну типізацію й ownership-перевірки. Автор unsafe-реалізації відповідає за валідність адрес, вирівнювання, ініціалізацію, межі доступу та коректність звільнення; гарантії безпечного API залежать від цих інваріантів.
- API використовує функції. Підтримка методів або UFCS для нього не потрібна.

| Операція | Контракт |
|---|---|
| `alloc(value)` | Виділити пам'ять для одного значення й одразу ініціалізувати її. Успішний результат вказує на ініціалізоване значення; публічної форми alloc без початкового значення немає. |
| `load(address)` | Прочитати значення за адресою. |
| `store(address, value)` | Записати значення відповідного типу за адресою. |
| `offset(address, index)` | Обчислити адресу зі зміщенням у кількості елементів T, а не байтів. Операція не доводить належність адреси виділеному блоку. |
| `free(address)` | Повернути відповідний виділений блок алокатору. Операція не замінює знищення вкладених owned-ресурсів. |

Умовний приклад для скаляра:

```python
unsafe:
    address: ptr[int] = alloc(42)
    result: int = load(address)
    store(address, 17)
    free(address)
```

Тип літерала в цьому прикладі задає явний контекст `ptr[int]`; це не запроваджує загальне виведення типів.

- Raw-вказівники й owned-масиви не є одним source-типом. Високорівневі масиви та об'єкти можуть розгортатися через AST desugaring у низькорівневі структури й операції з адресами.
- Компілятор може мати додаткові внутрішні операції, наприклад виділення пам'яті перед послідовною ініціалізацією складного об'єкта. Такі проміжні стани не повинні ставати доступними безпечному коду.
- Підтримка наведеного API не вимагає одразу реалізовувати загальні generics: операції можуть бути вбудованими функціями з окремими правилами компілятора.

## Відкриті питання

- Остаточні сигнатури, namespace функцій, представлення ptr і правила його копіювання та перетворень.
- Повідомлення про невдалу алокацію; успішний alloc не повертає порожнього вказівника.
- Контракти load/store для owning-значень: побітове копіювання не повинно неявно створювати другого власника. Приклади вище стосуються скалярів.
- Чи дозволений `free` для довільного `T`, чи перед ним потрібно явно знищити значення; звільнення блоку саме по собі не запускає деструктори вкладених ресурсів.
- Створення й ініціалізація динамічних буферів, їхня довжина та метадані для free. Одноелементний alloc(value) сам по собі не є алокацією буфера довільної місткості.
- Повний механізм побудови safe-власника над raw-пам'яттю, cleanup на виняткових шляхах і контракти FFI.
