# smalang

Проєкт простої мови програмування та власного компілятора. Мову планується розвивати невеликими кроками, зберігаючи короткий цикл компіляції.

## Цілі

- Компілювати програми в нативні виконувані бінарники для Linux x86_64.
- Орієнтуватися на швидкість компіляції Go; перевірити її на практиці після першого робочого зрізу й оптимізувати далі.
- Написати власний native backend для Linux x86_64.
- Тримати мову простою на початку й розширювати її в міру потреби.
- Розглянути C FFI на пізнішому етапі.

Проєкт зараз має початкову конфігурацію Crystal shard у `shard.yml`.
Файли smalang використовуватимуть розширення `.py` для сумісності з редакторами та підсвічуванням синтаксису; це вихідний код smalang, який потрібно буде компілювати.

## Напрямок синтаксису мови

Вихідний синтаксис буде Python-подібним. Для параметрів і результатів функцій потрібні явні анотації. Компілятор не вгадуватиме пропущені типи; типи виразів перевірятимуться за правилами операцій та їхніх операндів.

Для першого кроку лексера зафіксовано: він видає `NEWLINE`, `INDENT` і `DEDENT`; кожен рівень відступу — рівно чотири пробіли й вводиться послідовно; дедент може закривати кілька рівнів. Табуляції та `#`-коментарі не підтримуються.

Токени зберігають тип і байтовий діапазон у вихідному файлі; лексеми не копіюються. `TokenStream` утримує `SourceFile`, а позиції для діагностики визначаються за індексом початків рядків.

Парсер одразу будує AST. AST зберігається в індексованій arena: вузли посилаються один на одного через `NodeId`, а не через сирі вказівники. За синтаксичних помилок парсер повертає частковий AST із `ErrorNode` та діагностикою, відновлюючись усередині функцій; лексичні помилки поки зупиняють лексер. AST із діагностиками не передається далі. Парсер відповідає лише за синтаксис. Окремий семантичний прохід розв'язує імена й перевіряє типи; він не змінює AST і не генерує IR. Його результат зберігає той самий AST разом із таблицями семантичних фактів, прив'язаними до `NodeId`. Усі функції модуля видимі незалежно від порядку оголошення, тому рекурсивні виклики перевіряються як звичайні виклики функцій. Семантичний прохід зупиняється на першій помилці, а IR генерується лише після успішного аналізу.

Початковий зріз граматики: модуль містить лише функції; кожна функція має типізовані параметри й результат та рівно один `return expression`. Вирази — десяткові цілі літерали, ідентифікатори, прямі виклики, дужки й бінарні `+` та `-` однакового пріоритету з лівою асоціативністю. Унарний мінус і коми наприкінці списків не підтримуються.

```python
def increment(value: int) -> int:
    return value + 1

def main() -> int:
    return increment(41)
```

Перша версія підтримуватиме оголошення функцій, типізовані параметри й результати, виклики функцій та цілочисельні операції додавання й віднімання (`+`, `-`). Це лише ілюстрація стилю, а не остаточна специфікація мови.

Для виконуваної програми точкою входу буде `def main() -> int:`. Значення, яке повертає `main`, стане кодом завершення процесу.

У згенерованому ELF вихідна `main` матиме окремий символ `__smalang_user_main`. Спільний runtime надасть процесний `main`, який викличе згенерований `__smalang_entry` wrapper; той передасть результат і виняток runtime.

Початкові цілочисельні типи:

- `int` — знаковий тип розміру вказівника, аналог `isize`.
- `uint` — беззнаковий тип розміру вказівника, аналог `usize`.

Для цілі Linux x86_64 обидва типи мають ширину 64 біти.

## Архітектурний напрямок

Потік компіляції:

```text
код smalang → lexer → parser + AST → semantic analysis → AST-to-IR lowering → typed IR → власний backend Linux x86_64 → нативний бінарник
```

IR буде власним і не залежатиме від конкретної архітектури чи WebAssembly. Його зручно читати у WAT-подібній формі S-expression, але це буде лише запозичення текстового стилю: команди й семантика IR належатимуть smalang. WAT сам по собі є текстовим поданням саме WebAssembly, а не універсальним IR ([специфікація](https://webassembly.github.io/spec/core/text/conventions.html)).

У компіляторі IR зберігатиметься у типізованих структурах. S-expression буде лише дампом для перегляду й налагодження, без зобов'язання підтримувати його як формат серіалізації чи вхідний синтаксис.

IR матиме окреме від AST індексоване сховище: модуль володіє функціями за `FunctionId`, а кожна функція — локальними значеннями, інструкціями й блоками за ID. Зв'язки зберігатимуть ID, а не сирі вказівники; достатньо звичайних growable arrays, без власного bump allocator-а.

Початковий typed IR використовуватиме SSA-значення: параметри функції задають початкові значення, а кожна обчислювальна інструкція визначає рівно одне нове типізоване значення. Операнди посилаються на ці значення. Функції складатимуться з базових блоків; у першому зрізі кожна матиме один блок входу з лінійною послідовністю інструкцій, що завершується `return`. Наступні розширення додадуть `jump`, `branch`, `invoke` та `phi` для виняткових переходів і майбутніх керувальних конструкцій мови.

Typed IR розширюватиметься операціями `div` і `rem`, а також базовими блоками, `phi` та явними винятковими переходами. Це розширення не додає відповідний синтаксис до мови автоматично: AST і семантичний аналіз окремо визначають, які вирази дозволені у вихідному коді. Типи IR `isize` та `usize` відповідають типам smalang `int` і `uint`; їхню ширину визначає target. Для Linux x86_64 це 64 біти. Виклик має типізовану ціль: у першому зрізі це посилання на функцію модуля, надалі його можна розширити на зовнішні символи. Посилання на ціль виклику — це ідентичність рівня модуля; правило SSA «визначено один раз» стосується значень усередині функції.

У CFG `branch` вважає нуль хибним, а будь-яке ненульове ціле — істинним. Кожен виклик у IR подається як `invoke`: його результат визначається на звичайному ребрі, а непрозоре значення винятку — на винятковому. Винятки не передаються звичайними аргументами або результатами функцій.

Typed IR перевіряється до передачі наступному етапу: кожне SSA-значення має бути визначене до використання, типи операндів і результатів операцій мають узгоджуватися з сигнатурами, а кожен блок у початковому зрізі завершується `return`.

```lisp
(module
  (func @multiply (param %v0 isize) (param %v1 isize) (result isize)
    (block @entry
      (%v2 isize (mul %v0 %v1))
      (return %v2)))
  (func @increment (param %v0 isize) (result isize)
    (block @entry
      (%v1 isize (const 1))
      (%v2 isize (add %v0 %v1))
      (return %v2)))
  (func @main (result isize)
    (block @entry
      (%v0 isize (const 41))
      (invoke (call @increment %v0) (normal @normal %v1) (exception @unwind %v2)))
    (block @normal
      (return %v1))
    (block @unwind
      (resume %v2))))
```

Це діагностичний приклад форми дампу, а не окремий синтаксис чи формат обміну. IR має залишатися придатним до представлення майбутніх типізованих зовнішніх викликів; рішення ABI належать backend-у.

## Runtime-винятки та ділення

IR і backend працюють із перевіреним IR. Відоме під час компіляції ділення на нуль відхиляє семантичний етап до генерації IR; цей runtime-контракт стосується нуля, виявленого під час виконання. Такий випадок породжує перехоплюваний внутрішній вид помилки `DivisionByZero`. Для `int` ділення округлює частку до нуля, остача має знак діленого, а `INT_MIN / -1` дає `INT_MIN` і остачу `0`; для `uint` використовуються беззнакові ділення й остача.

Початкова модель генерує винятки лише з runtime-перевірок; явного користувацького `raise` і нових мовних enum/class/struct для винятків немає. Види помилок є внутрішніми мітками runtime; IR може зіставляти їх за видом або приймати будь-який виняток. Потенційно виняткова операція, зокрема кожен виклик функції в першій версії, завершує блок через `invoke` із звичайним та винятковим наступниками. Обробник отримує непрозоре SSA-значення винятку; злиття значень задаються явними `phi`. Cleanup-блоки є частиною моделі IR. Якщо cleanup породжує новий виняток під час розкручування, він стає активним, а попередній зберігається як suppressed error.

Backend формує `.eh_frame` CFI для системного Itanium unwinder і Smalang-owned LSDA у `.gcc_except_table`; Smalang personality зіставляє внутрішні kinds та керує cleanup. Runtime реалізовано як C-компонент, скомпонований у виконуваний файл, який використовує системний `libgcc_s` через `_Unwind_*` base ABI; C++ exception ABI не використовується. Внутрішній exception record починається з `_Unwind_Exception`, містить приватний kind і володіє ланцюгом suppressed exceptions.

Для stack trace backend генерує DWARF 5 `.debug_line` і `.debug_line_str`, а також мінімальні `.debug_info` та `.debug_abbrev` для звичайних DWARF-читачів. Runtime відновлює рядки з таблиці line info у виконуваному файлі та імена функцій із ELF symbol table. Під час створення винятку runtime зберігає адреси кадрів до початку розкручування; згенерований `__smalang_entry` має catch-all landing pad, який після виконання cleanup передає виняток runtime для друку й завершення процесу з ненульовим кодом. Виняткова модель, IR і backend не додають синтаксис `try/catch` чи `finally` до мови.

## Поки не визначено

- Повний обсяг Python-подібного синтаксису поза початковою граматикою вище.
- Оптимізація хвостових викликів і гарантія сталого використання стека для рекурсії.
- C FFI: синтаксис, відповідність типів smalang типам C, оголошення зовнішніх символів і компонування бібліотек.

Backend генеруватиме ELF64 relocatable object files. Системний C compiler driver `cc` компонуватиме їх із C runtime та зовнішнім linker-ом. Усі функції smalang для Linux x86_64 використовуватимуть System V AMD64 calling convention. Для майбутнього FFI IR має залишатися придатним до опису типізованих зовнішніх викликів, а ABI-логіка належатиме backend-у.

Перший backend-зріз прийматиме перевірений typed IR і сам формуватиме ELF64 relocatable object; він не генеруватиме assembly для зовнішнього assembler-а. Розподіл SSA-значень почнеться з linear scan: значення отримують регістр або spill slot, а значення, живі через виклик, тимчасово зберігаються у стеку. Backend також відповідатиме за System V AMD64 аргументи, повернення, вирівнювання стеку й relocations для внутрішніх викликів. AST-to-IR lowering є окремим проходом; compiler CLI залишається окремою майбутньою фічею.

## Roadmap

- Develop the compiler in separate features: lexer → parser + AST → semantic analysis → typed IR → native backend.
- Define and implement explicit overflow semantics for `int` and `uint`. The initial compiler slice does not guarantee behavior for overflowing arithmetic.
